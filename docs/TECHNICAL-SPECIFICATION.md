## 1. متطلبات بيئة التطوير (Development Requirements)

| المتطلب | القيمة | ملاحظة |
|---|---|---|
| Node.js (لتشغيل `npm install`/`electron-builder` نفسها) | غير محدَّد صراحة في `package.json` (لا يوجد حقل `engines`) | ⚠️ **فجوة توثيقية بسيطة** — يُنصح بإضافة `"engines": {"node": ">=16"}` لتفادي محاولة تثبيت على بيئة قديمة جداً غير متوافقة مع أدوات البناء الحديثة |
| مدير الحزم | npm (يوجد `package-lock.json` مُلتزَم فعلياً) | لا تستخدم `yarn` أو `pnpm` لتفادي تعارض ملفات القفل |
| نظام التشغيل للتطوير | يعمل على أي بيئة يدعمها Node.js/npm (macOS/Linux/Windows) | **لكن البناء النهائي (`npm run build`) ينتج حصراً مثبِّتات Windows** — هذا تطبيق Windows-only في مخرجاته النهائية |
| Git | مطلوب فعلياً — المشروع تحت تحكم إصدار فعلي (`.git/` موجود، سجل التزامات نظيف ومتسلسل) | يُستنسَخ عبر `git clone` (موثَّق في `README.md`) |

**خطوة إلزامية بعد `npm install`:**
```bash
npm install
# يُشغَّل تلقائياً عبر hook: postinstall
# → cd node_modules/better-sqlite3 && npx prebuild-install --runtime=electron --target=22.3.27
```
هذا السطر **حرج وليس تفصيلاً ثانوياً**: يفرض إعادة تجميع/تنزيل إضافة `better-sqlite3` الأصلية (Native Addon) مُبنيّة تحديداً لواجهة Electron الثنائية (ABI) للإصدار `22.3.27`، وليس لواجهة Node.js العادية المُثبَّتة على جهاز المطوّر. تجاهل هذه الخطوة (أو تشغيل `npm install` بعلم `--ignore-scripts`) ينتج خطأ تشغيل فوري عند فتح التطبيق (`NODE_MODULE_VERSION mismatch`).

## 2. سير عمل التطوير (Development Workflow)

| الأمر | الغرض |
|---|---|
| `npm start` | تشغيل التطبيق عادياً (`electron .`) |
| `npm run dev` | تشغيل مع فتح منفذ تصحيح (`--inspect=5858`) لربط أدوات تصحيح Node.js الخارجية |
| `npm run db:reset` | حذف ملف قاعدة البيانات الحية وملفات WAL/SHM المرافقة لها فقط (`scripts/reset-db.js`) — يبدأ من مخطط نظيف عند التشغيل التالي |
| `npm run dev:clean` | `db:reset` ثم `dev` متسلسلَين — بيئة تطوير نظيفة بالكامل من الصفر |
| `npm test` | يشغّل **الحارسين معاً بالتسلسل**: `tests/ipcChannelGuard.test.js` ثم `tests/leaveService.test.js` — يتوقف عند أول فشل (`&&`) |
| `npm run build` | يبني حزمة NSIS الإنتاجية لـ Windows عبر `electron-builder --win` |

**قاعدة أمان `scripts/reset-db.js` (موثَّقة داخل الملف نفسه):** يعمل **فقط** خارج عملية Electron (Node.js صرف)، ولا يلمس أي مسار خارج مجلد `userData` المُحلَّل، وكل عملية حذف مستقلة (ملف مفقود = تسجيل معلوماتي لا خطأ) لضمان أن السكربت **Idempotent** (آمن ضد التكرار).

## 3. البناء والتغليف (Build & Packaging)

### 3.1 مسار البناء المعتمد

يوجد مساران فعلياً في هذا المشروع، **والمسار المعتمد فعلياً هو الثاني**:

| المسار | الأمر | الحالة |
|---|---|---|
| القياسي عبر `electron-builder` CLI | `npm run build` → `electron-builder --win` | يعمل، يعتمد إعداد `build` في `package.json` |
| **البرمجي المخصَّص (المعتمد)** | `node scripts/build.js` | يضبط `process.noAsar = true` صراحة قبل الاستدعاء — **ضروري** لأن عملية Electron الحالية نفسها (التي يُشغَّل منها سكربت البناء أحياناً) تُفعِّل اعتراض ASAR الافتراضي، ما يمنع `electron-builder` من كتابة `app.asar` كملف ثنائي عادي في مجلد `release/` |

### 3.2 إعداد `electron-builder` الفعلي (`package.json`)

```json
"build": {
  "appId": "com.hr.holidays",
  "productName": "Holidays",
  "files": ["src/**/*", "node_modules/**/*", "package.json",
            "!scripts", "!scratch", "!backups", "!data", "!tests",
            "!*.db*", "!temp_*", "!*.txt", "!*.log"],
  "directories": { "output": "release" },
  "win": { "target": "nsis", "arch": ["x64", "ia32"] },
  "nsis": {
    "oneClick": false,
    "allowToChangeInstallationDirectory": true,
    "runAfterFinish": true,
    "shortcutName": "نظام الإجازات"
  }
}
```

**نقاط تقنية حرجة:**
- **`"arch": ["x64", "ia32"]`** (ADR-016): كل عملية بناء تنتج **مثبِّتين منفصلين** — واحد لكل معمارية. أي عملية توزيع أو تعليمات تثبيت للمستخدم النهائي يجب أن توضّح أيّ ملف يناسب أي جهاز (Windows 7 القديم 32-بت مقابل الأجهزة الحديثة 64-بت).
- **استثناءات `files`**: `!data`، `!backups`، `!*.db*` تضمن أن أي بيانات تطوير محلية (قاعدة بيانات تجريبية، نسخ احتياطية محلية) **لا تُشحَن أبداً** مع المثبِّت للمستخدم النهائي — فحص أساسي لمنع تسرّب بيانات تجريبية أو حساسة.
- **`oneClick: false`**: يمنح المستخدم اختيار مجلد التثبيت — مناسب لبيئة إدارية حكومية قد تتطلب تثبيتاً على مسار مخصَّص (مثال: قرص شبكي مشترك).

### 3.3 قيد الاعتماديات الأصلية (Native Dependencies) عند البناء

`better-sqlite3` إضافة C++ مُجمَّعة لهدف ثنائي محدَّد (Electron 22 / ABI 110). **أي محاولة بناء للمعمارية `ia32` يجب أن تتأكد من توفر Prebuild مطابق لـ Windows 32-بت تحديداً** (منفصل عن Prebuild الـ 64-بت) — هذا غير مضمون تلقائياً لكل إصدارات `better-sqlite3`، ويُنصح بالتحقق العملي (تثبيت واختبار فعلي على جهاز Windows 7 32-بت حقيقي) قبل أي توزيع رسمي على هذه الفئة من الأجهزة. **Cannot verify** توفر هذا الـ Prebuild فعلياً من داخل بيئة هذا الفحص (بيئة Linux بلا Windows حقيقي للاختبار).

## 4. تدقيق الاعتماديات المحدَّث (Dependency Audit — 10 أيلول 2026)

> هذا القسم محدَّث بنتائج `npm audit` فعلية على `package-lock.json` الحالي، وليس نسخة عن التدقيق الأول.

| الحزمة | النطاق | الخطورة | الحالة | ملاحظة |
|---|---|---|---|---|
| `brace-expansion` | تطويرية (`glob` ضمن `electron-builder`) | كانت عالية | ✅ **مُعالَجة** | أُصلحت عبر `npm audit fix` (Phase 2 من `AI_FIX_INSTRUCTIONS.md`) — لم تعد تظهر في الفحص الحالي |
| `uuid` (<11.1.1) | تشغيلية فعلية (عبر `exceljs`) | متوسطة | ⚠️ **لا تزال قائمة — قرار مقصود** | تقييم Phase 2 خلص إلى أن الإصلاح التلقائي (`--force`) يخفّض `exceljs` لإصدار قديم كاسر (3.4.0)؛ القرار المتّخذ هو **قبول المخاطرة مؤقتاً** بانتظار إصدار تصحيحي متوافق من `exceljs` نفسها بدل ترقية قسرية كاسرة |
| `adm-zip` (0.6.0) | تشغيلية فعلية (أرشفة حزم `.hbak`) | متوسطة | 🆕 **جديدة — لم تكن موثَّقة صراحة في التدقيق الأول** | ثغرة "اتباع الروابط الرمزية عند فك الضغط" (`GHSA-vwc7-r8mq-g2x9`) — قد تسمح نظرياً بالكتابة فوق ملف خارج مجلد الاستخراج المقصود إن كان أرشيف `.hbak` نفسه ملغوماً بروابط رمزية. **الأثر العملي محدود حالياً** لأن ملفات `.hbak` تُنشأ داخلياً بواسطة `AutoBackupService`/`system:backup` نفسه (مصدر موثوق)، لكن عملية `system:restore` تقبل ملف `.hbak` **مُختاراً من المستخدم** عبر `system:selectDirectory` — إن اختار المستخدم عن غير قصد (أو بسوء نية) ملف `.hbak` من مصدر خارجي غير موثوق، هذه الثغرة تصبح ذات صلة فعلية. **يُوصى بإضافتها لأول عنصر في دورة المراجعة الأمنية القادمة** — إصلاحها يتطلب ترقية كاسرة (`npm audit fix --force` يخفّض `adm-zip` لإصدار 0.5.8) تحتاج اختباراً كاملاً لمسار الاستعادة قبل اعتمادها |
| `electron` (22.3.27) | إطار العمل | — | By Design (ADR-002/ADR-013) | مثبَّت بدقة لأسباب توافق Windows 7/8.1 — لا يُحدَّث كتحديث أمني روتيني |
| `better-sqlite3` (8.7.0) | قاعدة البيانات | — | مثبَّت بدقة | مرتبط بـ ABI الخاص بـ Electron 22 |
| `electron-builder` (^24.9.0) | تطويرية فقط | — | لا تُشحَن مع المنتج النهائي | — |

**خطة المتابعة الموصى بها لثغرة `adm-zip` (لم تُنفَّذ بعد ضمن أي Phase سابقة):**
1. التحقق أولاً هل الإصدار 0.5.8 (الهدف بعد `--force`) يحافظ على نفس واجهة الاستدعاء (API) المستخدمة فعلياً في `database.js`/`AutoBackupService.js` — إن كانت متطابقة، الترقية منخفضة المخاطر رغم تصنيفها "كاسرة" رسمياً في `npm audit`.
2. بديلاً، وبغض النظر عن قرار الترقية: إضافة تحقق صريح في مسار `system:restore` يرفض أي حزمة `.hbak` تحتوي إدخالات هي روابط رمزية (Symlink Entries) قبل تمريرها لـ `adm-zip` أصلاً — طبقة حماية إضافية مستقلة عن إصدار المكتبة نفسها، على نمط `DocumentStorageService.js` (ADR-006 بروح الدفاع في العمق).

## 5. البنية التحتية للاختبار (Testing Infrastructure)

| الملف | النوع | التغطية |
|---|---|---|
| `tests/ipcChannelGuard.test.js` | حارس بنيوي (Structural Regression Guard) | تطابق 47 قناة IPC بين `preload.js` والمعالجات الفعلية بدقة 100% |
| `tests/leaveService.test.js` | اختبارات وحدة (Unit Tests) | 17 كتلة اختبار / ~70 تأكيداً (Assertions)، تغطي: الأيام الفردية، تواريخ مقلوبة، سنوات كبيسة، تداخل الإجازات، عجز الرصيد (اعتيادي ومرضي)، التوزيع الهرمي على الشرائح الثلاث، استرجاع دقيق عند الحذف، عبور حدود الشهر/السنة، تحويل نوع الإجازة، تزويد تلقائي لموظف جديد، واستثناء الموظفين المنقولين من 5 استعلامات مختلفة (نشط اليوم، مُصفَّح، تنبيهات قريبة، أرصدة حرجة، تراكم سنوي) |

**آلية تقنية جديرة بالتوثيق — جسر ABI الشفاف:**
```js
// tests/leaveService.test.js (الأسطر 22-31)
if (!process.versions.electron && process.env.ELECTRON_RUN_AS_NODE !== '1') {
  const { spawnSync } = require('child_process');
  const electronPath = require('electron');
  const result = spawnSync(electronPath, [__filename], {
    stdio: 'inherit',
    env: { ...process.env, ELECTRON_RUN_AS_NODE: '1' },
  });
  process.exit(result.status ?? 0);
}
```
حل تقني أنيق لمشكلة حقيقية: `better-sqlite3` مُجمَّعة لـ ABI الخاص بـ Electron 22 (§1 أعلاه)، فتشغيل الاختبار عبر `node` النظامي مباشرة سيفشل بخطأ عدم تطابق ABI. الحل: الاختبار يكتشف أنه لم يُشغَّل داخل بيئة Electron، فيعيد تشغيل نفسه عبر ثنائي Electron نفسه بوضع `ELECTRON_RUN_AS_NODE=1` (وضع يجعل Electron يتصرف كـ Node.js صرف بلا نافذة رسومية) — يحصل بذلك على ABI الصحيح تلقائياً دون أي إعداد يدوي إضافي من المطوّر.

**⚠️ قيد بيئي مؤكَّد أثناء إعادة الفحص هذه:** تعذَّر تنفيذ `npm test` فعلياً وإثبات النجاح داخل بيئة هذا التدقيق (حاوية Linux بلا واجهة رسومية ولا ثنائي Electron قابل للتشغيل الفعلي لهدف Windows). حارس `ipcChannelGuard.test.js` نجح فعلياً (لا يعتمد Electron)، لكن `leaveService.test.js` **لم يُنفَّذ فعلياً** — التحقق من صحته تم عبر **قراءة الكود سطراً بسطر وتتبّع الحسابات يدوياً** (مثال: التحقق اليدوي من حالة العجز 130 يوماً المطلوبة مقابل رصيد 120 يوماً ينتج توزيعاً 30/45/55 برصيد سالب 10- في الشريحة الأخيرة — مطابق تماماً لتأكيدات الاختبار). **Cannot verify** نتيجة التنفيذ الفعلي دون بيئة Windows حقيقية أو محاكي مناسب.

## 6. معايير الترميز الملاحَظة فعلياً (Observed Coding Standards)

لا يوجد ملف `.eslintrc`/`.prettierrc`/`.editorconfig` في المشروع (تم التحقق — **فجوة أدوات فعلية**، لا معيار آلي مفروض)، لكن الأنماط التالية **مُطبَّقة يدوياً وباتساق ملحوظ** عبر كامل الشيفرة:

| المعيار | التطبيق |
|---|---|
| غلاف استجابة IPC موحَّد | كل معالج يُغلَّف بـ `safeHandle()` (`utils/ipcHandlerHelper.js`) → دائماً `{success, data}` أو `{success, error}` |
| ترجمة الأخطاء للعربية | `utils/fileErrorTranslator.js` و`utils/sqliteErrorTranslator.js` يحوّلان أخطاء النظام/SQLite الخام (الإنجليزية، الفنية) لرسائل عربية مفهومة قبل وصولها للواجهة — **لا رسالة خطأ تقنية خام تصل المستخدم النهائي مباشرة** |
| تسجيل موحَّد | `LoggerService.info/warn/error(context, message)` بدل `console.*` المباشر — مُطبَّق الآن بالكامل بعد تنظيف N4 (صفر استدعاءات `console.log` متبقية في `src/`) |
| توثيق JSDoc | كل دالة عامة في `services/*.js` موثَّقة بتعليق JSDoc عربي/إنجليزي مزدوج يوضّح المعاملات والقيمة المُعادة |
| تعليقات ثنائية اللغة | تعليقات الكود عربية وإنجليزية معاً بنمط ثابت (`// الوصف العربي / English description`) — يخدم فريقاً قد يحتاج المرجعين معاً |
| لا استخدام إطار عمل واجهة | راجع `ARCHITECTURE.md` §3.1 وADR-012 |

**توصية تحسينية (غير عاجلة):** إضافة `.eslintrc` بسيط (حتى بقواعد أساسية: `no-unused-vars`، `no-console` لمنع تكرار مشكلة N4 مستقبلاً) لتثبيت هذه الأنماط اليدوية آلياً بدل الاعتماد فقط على انضباط الفريق.

## 7. القيود التقنية الحاكمة (Governing Technical Constraints)

ملخص مُجمَّع من `DECISIONS.md` للرجوع السريع عند اتخاذ أي قرار تقني جديد:

1. **لا ترقية لـ `electron` أو `better-sqlite3` كإجراء روتيني** — أي تغيير يفرض إعادة تقييم دعم Windows 7/8.1 بالكامل (ADR-002، ADR-013 لا يزال مفتوحاً جزئياً).
2. **أي ملف HTML جديد أو مُعدَّل يجب أن يمتثل لـ CSP الصارم** — بلا `onclick=`/`style=` مضمَّنة، بلا `<script>` مضمَّن (ADR-017).
3. **أي وصول لملف عبر مسار مُدخَل أو مخزَّن يجب أن يمر عبر تحقق احتواء المسار** (نمط `DocumentStorageService.js`، ADR-006 بالروح نفسها) — وهذا **ينطبق الآن أيضاً على ثغرة `adm-zip` المذكورة أعلاه** كخط دفاع مستقل عن قرار ترقية المكتبة.
4. **أي قناة IPC جديدة تُسجَّل في `VALID_CHANNELS` أولاً** — `npm test` سيفشل تلقائياً عند النسيان (ADR-011).
5. **أي منطق أعمال جديد للإجازات يعيش في `LeaveService.js`**، لا في طبقة `ipc/` (تم فرضه فعلياً بعد N3).
6. **أي تعديل على أعداد أيام/نسب الإجازة المرضية يتطلب ترحيل SQL** يعيد بناء `LeaveBalances` (وليس تعديل JS وحده) — قيد `CHECK` صارم على مستوى القاعدة (`DATA-MODEL.md` §2.3، ADR-005/014).
